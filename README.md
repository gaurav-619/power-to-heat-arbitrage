# Celsio Prototype — Industrial Electrification Decision Tool

A prototype that answers one question for a synthetic German industrial plant: **in any
given hour, is it cheaper to run a gas boiler or an electric heater?**, using real German
day-ahead electricity prices and real historical weather, then rolls that hourly decision
up into an annual cost comparison, a forecast-quality check, and a CAPEX payback
sensitivity table.

## Real vs. synthetic data — what's actually real

Three tiers, not two — matching the `VERIFIED`/`ASSUMED` distinction `config/assumptions.yaml`
already makes internally (a number's *source* being real doesn't depend on whether it was
fetched by an API call or looked up by hand):

| Component | Status | Detail |
|---|---|---|
| Day-ahead electricity prices | **Real, live-fetched** | SMARD (Bundesnetzagentur) API, filter 4169, DE-LU, hourly |
| Weather / temperature | **Real, live-fetched** | Open-Meteo API, Ludwigshafen (49.48, 8.45) |
| Gas price, gas/electric efficiency, electricity markup, CAPEX | **Real, cited (not live-fetched)** | Marked `VERIFIED` in `config/assumptions.yaml` — genuine external sources (EEX gas futures, published German industrial electricity levies, McKinsey/US DOE CAPEX studies), hand-researched rather than pulled from an API, with arithmetic shown for anything derived. Real numbers, just static. |
| The plant itself (base load, temperature sensitivity, reference temperature) | **Synthetic — invented for this prototype** | No such plant exists and these three parameters have no external source at all — marked `ASSUMED`, low confidence, in `config/assumptions.yaml` |
| Location (Ludwigshafen as the weather proxy) | **Synthetic choice** | The weather *data* for this coordinate is real (see above); using it to represent "a generic German industrial site" is the assumption — it is not a claim about any real facility there |

## Scope boundary

This is a decision-support **prototype**, not a production forecasting or trading system.
In scope: hourly gas-vs-electric switching logic on historical actual prices, a simple
weather-driven demand model, a first-pass price forecast, and a CAPEX payback range. Out of
scope: real-time operation, actual plant integration, regulatory/permitting analysis,
non-thermal loads, any consumer class other than large industrial baseload, and any carbon
price or emissions accounting (see Known Limitations).

```
  dbt_project/models/marts/         annual costs, forecast backtest, payback table
  config/assumptions.yaml    every model input, with source + confidence
  tests/                     pytest: decision logic, tz/DST join, unit conversion
  dashboard/app.py           Streamlit dashboard

  .github/workflows/daily_refresh.yml

```

**Why `celsio.duckdb` is committed despite being a build artifact:** Streamlit Community
Cloud only runs `pip install` + `streamlit run` — it never runs the ingestion scripts or
`dbt run`. Without a committed snapshot the deployed dashboard would have nothing to read.
The dashboard only queries materialized `marts`/`intermediate` tables, never the CSV-backed
staging views, so the `.duckdb` file alone is sufficient (verified by removing the CSVs
locally and confirming the dashboard still renders correctly). Regenerate it locally any
time with the pipeline commands below, then re-commit if you want the deployed dashboard
to reflect a fresher run.

## Setup

Requires Python 3.11 (pinned in `requirements.txt`; if only a newer Python is on your
`PATH`, install 3.11 with `uv python install 3.11` and create the venv with
`uv venv --python 3.11 .venv`).

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

## Running the pipeline

```bash
python ingestion/fetch_prices.py     # prints the resolved date range, writes data/processed/prices.csv
python ingestion/fetch_weather.py    # writes data/processed/weather.csv
cd dbt_project
dbt run --profiles-dir .             # builds staging -> intermediate -> marts into data/processed/celsio.duckdb
cd ..
pytest tests/ -v
streamlit run dashboard/app.py
```

dbt commands must be run from inside `dbt_project/` (relative paths in the models assume
that working directory — see `dbt_project/dbt_project.yml`).

## Date range

Ingestion always targets the most recent full 12 months, ending 2 days before the run date
(`end_date = today - 2 days`, `start_date = end_date - 365 days`), computed and printed at
the start of each fetch script. The currently-committed data snapshot covers
**2025-08-14 through 2026-08-14** (366 days / 8,784 hourly rows — 2026 is a leap year).
Re-running the pipeline on a later date shifts this window forward and every figure below
moves slightly (typically well under 1%) — see `PITCH.md` for the full methodology and a
worked example tracing one real hour end to end.

## Decision logic

For every hour: `gas_cost_per_mwh = gas_price / gas_boiler_efficiency`,
`electric_cost_per_mwh = (day_ahead_price + electricity_markup) / electric_heater_efficiency`,
each multiplied by that hour's `total_demand_mwth` (base load + weather-driven extra
demand below 15°C). The cheaper option is "smart switching"; always using gas is the
baseline. `tests/test_decision_logic.py` hand-verifies 4 example hours (2 gas-favoring, 2
electric-favoring) and asserts `sum(smart_switching_cost) <= sum(always_gas_cost)` holds on
every one of the 366 days in the dataset — it does, with zero exceptions.

## Retrospective annual cost result (actual historical prices, full ingested year)

| Strategy | Annual cost |
|---|---|
| Always gas | EUR 1,621,531 |
| Smart switching | EUR 1,523,905 |
| **Savings** | **EUR 97,626 (6.0%)** |

Electricity was the cheaper option in 1,028 of 8,784 hours (11.7%) — mostly overnight /
high-wind hours when the day-ahead price drops low enough to beat gas even after the
electricity markup.

## Forecasting: seasonal-naive vs. persistence

Seasonal-naive = mean of the preceding 4 occurrences of the same Europe/Berlin
weekday+hour. Persistence = same hour, previous calendar day. Backtested over 8,111 hours
(the full year minus the first 4 weeks, which the seasonal-naive method needs as history).

| Method | MAE (EUR/MWh) | MAPE* |
|---|---|---|
| Seasonal-naive | 31.42 | 138.1% |
| **Persistence** | **28.10** | **96.4%** |

**Persistence wins on both MAE and MAPE.** Day-ahead prices are volatile and mean-reverting
at an hourly scale faster than a 4-week seasonal pattern captures, so yesterday's actual
price at the same hour is a better predictor than the multi-week seasonal average.

\* MAPE is computed only over the 7,805 hours with |actual price| >= EUR 1/MWh — German
day-ahead prices go negative or near-zero often enough that including those hours makes
MAPE explode/undefined (see Known Limitations).

## Payback sensitivity (9-cell)

`payback_years = capex_eur_per_mwth[scenario] * plant_base_load_mwth / annual_savings_eur`,
recomputed per gas-price scenario (electric cost is unaffected by the gas price):

| CAPEX \\ Gas price | -20% (EUR 30.57) | base (EUR 38.21) | +20% (EUR 45.85) |
|---|---|---|---|
| low (EUR 125,000/MWth) | 7.9 yrs | 5.1 yrs | 3.7 yrs |
| mid (EUR 137,500/MWth) | 8.7 yrs | 5.6 yrs | 4.0 yrs |
| high (EUR 150,000/MWth) | 9.5 yrs | 6.1 yrs | 4.4 yrs |

Never quote a single payback number from this table — the range (3.7 to 9.5 years) is the
honest answer given CAPEX and gas-price uncertainty.

## Data sources & attribution

- **SMARD (Bundesnetzagentur)** — day-ahead price, filter 4169, DE-LU, hourly resolution.
  `https://www.smard.de/app`. Since 1 Oct 2025 EPEX auctions clear at 15-minute resolution,
  but SMARD continues to publish this same hourly series across that boundary, so the
  hourly series is used for the whole date range for consistency.
- **Open-Meteo** — historical weather archive, `https://archive-api.open-meteo.com/v1/archive`,
  no API key required.
- Gas price, electricity markup, and CAPEX figures — see the `source` field of each entry
  in `config/assumptions.yaml` for the exact citation and, where a number is derived, the
  arithmetic (e.g. gas price is the midpoint of two 2025/2026 published projections).

## Known Limitations

- **No carbon price.** Neither an EU ETS carbon price nor any carbon-related levy is
  included in either the gas or electricity cost formula. A meaningful carbon price would
  shift the switching threshold toward electricity more often than shown here.
- **CAPEX figures are not 2026-dated or Germany-specific.** The verified CAPEX range comes
  from a 2024 McKinsey European analysis cross-validated against a 2018-USD-basis US DOE
  cost model — no public 2026-dated, Germany-specific electric-boiler CAPEX figure was
  found. Treat the payback range as directional, not precise.
- **Consumer-class consistency, not universality.** Gas price, electricity markup, and
  CAPEX all assume the same large-industrial baseload consumer class so the three-way
  comparison is apples-to-apples — but that also means none of these figures apply to a
  smaller or differently-classed consumer.
- **MAPE is unstable for electricity prices.** Day-ahead prices go negative or near-zero
  often enough (346 of 8,784 hours in the full dataset, 306 of 8,111 in the backtest window,
  have |price| < EUR 1/MWh) that MAPE is undefined or explosive for those hours; this
  prototype excludes them from the MAPE calculation only (MAE uses every hour). Treat the
  reported MAPE figures as a secondary indicator, MAE as primary.
- **Weekly-lag forecasting uses wall-clock (weekday, hour) matching, not a fixed 168-hour
  shift**, specifically so it stays correct across the DST transition weeks — but this also
  means the two DST transition days (2025-10-26 fall-back, 2026-03-29 spring-forward) have
  25 and 23 local hours respectively rather than the usual 24, verified in
  `tests/test_timezone_join.py`.
- **Ludwigshafen is a single-point weather proxy** for "a generic German industrial site,"
  not a real facility — a different location would shift the temperature-driven demand
  component materially.
- **The demand model is a simplified heating-degree threshold**, not a real thermodynamic
  building/process model (see `reference_temperature_c` and
  `temp_sensitivity_coefficient_mwth_per_c` in `config/assumptions.yaml`, both marked
  `ASSUMED`, low confidence).

## Deployment

The dashboard is deployed on [Streamlit Community Cloud](https://share.streamlit.io) directly
from this repo:

- **Main file path:** `dashboard/app.py`
- **Python version:** 3.11 (set in the deploy UI's Advanced settings — Streamlit Cloud does
  not read a `runtime.txt` or `.python-version` file)
- **Dependencies:** `dashboard/requirements.txt`, not the repo-root `requirements.txt`.
  Streamlit Cloud checks the entrypoint's own directory for a dependency file before
  falling back to the repo root, so this trimmed file (just `streamlit`, `duckdb`, `pandas`,
  `pyyaml` — everything `dashboard/app.py` actually imports) takes priority and keeps the
  cloud build fast, without installing `dbt-core`, `pytest`, and the rest of the full
  pipeline's dependencies for a page that only ever reads an already-built DuckDB file.
  Verified locally by installing only that file into an isolated venv and confirming the
  dashboard still runs correctly.
- **Data:** reads the committed `data/processed/celsio.duckdb` snapshot (see Project
  structure above) — the deployed app never calls the SMARD or Open-Meteo APIs itself.

To redeploy with fresher data: run the pipeline commands below locally, commit the
regenerated `celsio.duckdb`, and push — Streamlit Cloud redeploys automatically on push to
the connected branch.
